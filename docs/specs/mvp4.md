# MVP4 — independent advanced capabilities

Software implemented on 2026-10-10 at the user's request. Memory, deterministic automation and optional local wake listening have separate switches and acceptance. Browser/live-speech/Pi checks from MVP3 remain open; progressing software here does not close those gates. No MQTT, generic HA service tool, natural-language rule activation or new device permissions.

## Approved preferences

Memory defaults to disabled in SQLite, including on upgrade. `POST /preferences/control` accepts exactly `{"enabled":true,"consent":true}` to enable or `{"enabled":false}` to disable. It returns `{"enabled":boolean}`; `GET /preferences` reports the same persisted setting alongside saved preferences. Changes apply to subsequent HTTP/WebSocket chat turns and to voice turns when recognition hands off to chat processing, without restarting. Once chat processing starts, a turn retains its earlier snapshot. The retired `MEMORY_ENABLED` environment variable is ignored. The settings panel and `/preferences` API allow explicit inspect/save/replace/delete even while context injection is disabled. `POST /preferences` requires `consent:true`, a strict category/value pair, and optionally an existing `sourceConversationId`. Allowed pairs are `response_language` (en/es) and `response_style` (concise/detailed), at most one of each. Changing a category replaces its value and approval timestamp while retaining its ID. Provenance is operator approval, timestamp and optional conversation reference. No agent memory-write tool exists.

SQLite migration 3 adds approved preferences; migration 4 adds automation storage; migration 5 adds persisted memory control without altering preferences, history, audits or automation state. Existing histories/audits are preserved. Preferences persist until replaced or deleted; there is no implicit extraction from conversations. Each new turn reads the current approved records when enabled. The Strands adapter translates only recognized enum values to fixed presentation instructions; arbitrary memory content never enters the system prompt or changes tool grants. At most two fixed instructions enter context. Deletion removes active storage and subsequent context, including subsequent turns in an existing conversation. A turn already running has its earlier snapshot. Historical responses, source conversations and separately retained backups are not erased by preference deletion. Backup deletion/rotation belongs to the operator.

## Deterministic light automations

`AUTOMATIONS_ENABLED=false` by default. Database global execution also starts disabled; both the server switch and an explicitly approved persisted global activation are necessary. Each rule starts disabled and requires its own `consent:true` activation. Approved activation persists across restart, as does emergency stop. The API/web use the existing local single-user trust boundary and origin checks; retain loopback/SSH deployment until household authentication is separately implemented. Satellite bearer credentials authorize voice only, not these routes.

A rule contains a name, one visible `light.*` transition to on/off, one explicitly write-granted light on/off action, and a 60–86400-second cooldown. Maximum 16 rules. Rule names are display data, never prompts. Editing is delete/recreate, followed by fresh activation. All rules, including disabled ones, participate in directed device-cycle rejection. Self-loops are rejected. The initial path uses the existing HA REST snapshot adapter, avoiding a new MQTT/event dependency. `AUTOMATION_POLL_MS` is 1000–60000 (default 5000). First startup, enable and recovery snapshots establish a baseline; no historical events are replayed. Snapshot polling may miss transitions shorter than the poll interval.

Events have runtime UUIDs and observation timestamps. Before reservation, reject events over 10 seconds old or over 2 seconds in the future. Durable event-ID deduplication survives restart; IDs retain seven days and older timestamps are rejected. A SQLite transaction checks current global/rule activation, cooldown and the global cap of four attempts in any 60-second window, then creates a conversation and pending receipt before physical dispatch. Denied/failed/uncertain attempts consume limits too. Pending reservations are never replayed. Dispatch uses `DirectLightControl` → `DeviceTools` → current write policy → pending-first audit → gateway. Receipts link to conversation audit; an incomplete receipt requires inspection. No action retry occurs within an attempt. A later genuinely new transition may start a new attempt after cooldown; disable the rule/global execution while investigating uncertainty.

A failed snapshot resets the baseline. If receipt finalization fails after dispatch, the pending receipt remains; the same event is not retried. Emergency stop persists before returning and prevents subsequent dispatches; it cannot undo an operation already dispatched. Historical receipts/audits are retained, including after rule deletion. The API returns the latest 50 receipts; there is no automatic historical audit purge.

Routes: `GET/POST /automations`, `DELETE /automations/:id`, `POST /automations/control`, `POST /automations/:id/activation`, `POST /automations/:id/dry-run`. Activation is `{enabled:true,consent:true}`; disable is `{enabled:false}`. Dry-run takes a strict transition event and reports match/current authorization/activation without action, audit, deduplication or cooldown consumption. Actual dispatch rechecks runtime gates. Events cannot be injected through a public execution endpoint; the composition root owns polling.

## Optional wake satellite

The user approved `@picovoice/porcupine-node` **4.0.2**. It is installed only in the satellite workspace and dynamically loaded by the separate wake executable. Default push-to-talk/one-turn flows do not initialize it. `WAKE_ENABLED=true` and the operator's private `PICOVOICE_ACCESS_KEY` are required; the engine can require vendor entitlement/activation connectivity. No claim of fully offline license initialization is made. The application sends no pre-wake audio to Aura/OpenAI. Check the account's current production terms separately from the SDK wrapper's Apache-2.0 license.

Wake CLI starts muted; `u` arms local listening, `m` aborts listening/capture/playback, `q` exits. Status distinguishes muted, muting, listening, activated and turn. Local raw PCM is framed to the SDK's sample rate/frame length with only a partial frame retained. Detection closes `arecord` before a local feedback beep, then captures a new command through the bounded existing VAD/voice pipeline. Say the keyword, wait for the beep, then speak. The wake phrase audio is discarded. Listening resumes only after the whole turn and playback finish; feedback/playback cannot self-trigger capture. Any engine/audio/transport failure returns to muted without automatic retry. Muting after submission cannot undo an accepted action; inspect history/audit before unmuting.

The bundled English keyword is **Porcupine**, not Aura. An operator-supplied platform-specific `.ppn` can provide a custom keyword; a matching `.pv` is needed for another language. Raspberry Pi 3/4/5 support is documented by the vendor, but this project's accuracy, CPU/memory budget, microphone, activation latency and playback echo remain unmeasured on target hardware. Mute is software-controlled; use hardware mic mute where available. No always-listening browser mode is added.
